## 0. Задание агенту

Создай библиотеку **динамического управления жизненным циклом Effect-сервисов**. Обычные `Layer` и `Effect` должны оставаться единицами реализации. Библиотека добавляет регистрацию компонентов во время работы, отслеживание доступности их зависимостей, остановку и повторную сборку затронутой части графа.

Не ограничивайся проектированием: после проверки возможностей установленного Effect последовательно реализуй этапы из раздела 19, запусти проверки и представь проверяемый результат. Не заменяй работающие тесты рассуждениями о том, что код «должен работать».

Приоритеты, по убыванию:

1. Корректное владение ресурсами и порядок остановки.
2. Отсутствие гонок публикации и использования устаревших экземпляров.
3. Типобезопасное описание зависимостей.
4. Маленький понятный API и совместимость с обычными Effect Layer.
5. Диагностируемость.
6. Оптимизация производительности.

Это **не** задание создать распределённую платформу, инфраструктурный фреймворк или полноценный клон Cordis. Не добавляй транспорт, загрузчик npm-плагинов, UI, БД и production-интеграции.

Если работа ведётся в существующем репозитории, сначала прочитай его инструкции и состояние. Не удаляй чужие файлы, не переписывай историю Git, не выполняй deployment или публикацию пакета. Небольшие изменения формы API допустимы после type-check spike; смысловые гарантии этой спецификации менять нельзя без явного описания в ADR.

## 1. Контекст и поправки к исходной идее

Исходная мотивация: поведение наподобие Cordis — зависимость появилась, потребитель запустился; зависимость исчезла, потребитель остановился; зависимость вернулась, потребитель построился заново — но с ресурсами и вычислениями на Effect.

Нельзя исходить из следующих неверных упрощений:

**«Effect Layer бывает только статическим».** В Effect v3 уже есть `Layer.suspend`, `Layer.flatMap`, `Layer.unwrapEffect` и `Layer.unwrapScoped`. Вычислить рецепт слоя из функции или Effect — существующая возможность, не новизна этой библиотеки. [S1]

**«В Effect нет перезагрузки сервисов».** Есть `Reloadable` и `ScopedRef`; отдельно есть экспериментальный `LayerMap` с доступом по ключу и invalidation. Их необходимо изучить, но они не являются готовой реализацией всех контрактов из этого handoff. В частности, смена значения в ссылке сама по себе не пересобирает потребителей, которые уже захватили старый объект. [S2–S4]

**«Произвольный Effect является реактивным условием».** Effect описывает вычисление. После выполнения он сам не сообщает, когда прочитанные им внешние данные изменились. Источник изменений должен быть явным: например, `SubscriptionRef`, поток событий или последующая контролируемая алгебра требований. У `SubscriptionRef.changes` есть и начальное значение, и дальнейшие изменения. [S5]

**«Закрыть Scope — значит гарантированно мгновенно уничтожить всё».** Scope запускает зарегистрированные finalizers. Это не механизм принудительного завершения произвольного JS, неучтённого Promise или внешнего процесса. Interruptibility, ошибки release и корректная регистрация ресурсов остаются существенными. [S6–S7]

**«Cordis Fiber и Effect Fiber — одно и то же».** Не использовать такое соответствие как основание реализации. Термины из разных библиотек не обязаны иметь одинаковую семантику.

Предмет разработки сформулирован уже и точнее:

> Поддерживать изменяемый граф доступных сервисов, управлять поколениями их scoped-реализаций и согласованно останавливать/пересобирать зависимые поколения.

Не заявлять научную новизну, уникальность в экосистеме или production-ready статус.

## 2. Основной пользовательский сценарий

Граф:

```text
Database → Analytics → ViewModel
```

Здесь стрелка означает «от провайдера к потребителю».

Последовательность:

```text
зарегистрировать Analytics и ViewModel
    Analytics = Pending: отсутствует Database
    ViewModel = Pending: отсутствует Analytics

зарегистрировать Database
    Database#1  = Active
    Analytics#1 = Active, использует Database#1
    ViewModel#1 = Active, использует Analytics#1

disable(Database)
    немедленно отозвать публикации затронутой ветки
    закончить/прервать управляемых потребителей
    закрыть ViewModel#1
    закрыть Analytics#1
    закрыть Database#1
    Database = Disabled
    Analytics и ViewModel = Pending

enable(Database)
    Database#2 → Analytics#2 → ViewModel#2
```

Отдельная ветка графа не должна перезапускаться из-за этих изменений.

`replace(Database, новый рецепт)` выполняет аналогичный stop/start, даже если оба рецепта предоставляют один и тот же Tag. **Новая реализация — новое поколение**, даже при совпадении ссылочной идентичности возвращённого объекта.

## 3. Технологический baseline и обязательный compatibility spike

Базовая реализация — **Effect 3.x**, TypeScript strict, ESM. Это сознательное ограничение первого выпуска, а не утверждение о том, какая major-версия Effect новейшая.

Проверенные исходники в этой спецификации относятся к официальной ветке `v3`. На момент подготовки её `packages/effect/package.json` содержит `3.22.2`, но это **не подтверждение публикации этой версии в npm**. Номер последнего опубликованного v3-релиза нужно проверить перед установкой. Не смешивай ветку `main`, документацию Effect v4 и v3-пакеты: официальный migration guide описывает изменения API между major-версиями. [S8–S9]

Перед реализацией:

```sh
pnpm view effect dist-tags --json
pnpm view effect versions --json
```

Выбери опубликованную stable-версию `3.x`, зафиксируй точную devDependency и lockfile. Для `@effect/vitest` проверь совместимые peerDependencies. Не устанавливай `effect@rc` или `effect@beta` неявно. Если npm недоступен, явно запиши ограничение; не выдавай непроверенный набор версий за проверенный.

Пакет должен иметь `effect` как peerDependency, а не включать собственную копию runtime в bundle. Диапазон peerDependencies не должен обещать версии, для которых используются отсутствующие API. Сначала честно поддерживать протестированный диапазон, затем расширять его через CI.

### 3.2. Что проверить маленькими исполняемыми тестами до основного кода

Создай `docs/compatibility.md` с точными версиями и результатами:

- `Layer.buildWithMemoMap` + явно принадлежащий поколению Scope.
- Запуск finalizers при успешной работе, failed acquisition и interruption.
- Повторная сборка одного и того же объекта Layer с разными входными Context и разными MemoMap.
- Жизнь `forkScoped`-задачи после завершения acquisition и её остановка вместе с поколением.
- Начальное значение и изменения `SubscriptionRef.changes` без окна между чтением и подпиской.
- Поведение `Reloadable`, `ScopedRef` и `LayerMap`: что можно переиспользовать и чего не хватает для наших контрактов.
- Сохранение caller Context/FiberRefs в управляемом пользовательском вызове.

Пользоваться **публичными** API Effect. Чтение исходников допустимо; импорт из `effect/internal/*`, monkey patching и разбор приватного AST Layer — нет.

Не пытайся поддержать v3 и v4 одновременно в первом выпуске. Не продолжай писать неподтверждённые сигнатуры «по памяти».

## 4. Границы версии 0.1

### Входит

Регистрация готовых TS-описаний во время работы; один публикуемый Tag на компонент; обязательные зависимости; наличие/отсутствие провайдера; независимый boolean gate; enable/disable; замена рецепта; unregister; каскадная инвалидация; scoped acquisition; диагностика состояния; безопасный управляемый вызов сервиса; ручной повтор failed acquisition.

### Не входит

Несколько провайдеров одного Tag, приоритеты и автоматический failover; optional/OR/динамический `flatMap` требований; произвольный Effect как автоматически реактивное условие; автоматический health-check; workflow persistence; RPC/NATS/HTTP; загрузка кода из файлов/npm; HMR; UI-компоненты; распределённые leases; sandbox для недоверенных плагинов; zero-downtime replacement; автоматическое повторение бизнес-команд; полная совместимость со всеми изменениями FiberRefs, производимыми произвольными Layer.

Файлы, события сети и health-check в будущем — **адаптеры источников изменений**, а не часть ядра.

Для первого выпуска нормально полностью пересчитывать небольшой DAG после изменения. Не нужен incremental computation engine. Нельзя полностью пересоздавать все живые сервисы: нетронутые поколения должны сохраняться.

## 5. Модель типов

Предпочтительное имя основного типа:

```ts
DynamicLayer<ROut, E, RIn>
```

Смысл параметров близок к `Layer<ROut, E, RIn>`:

- `ROut` — идентификатор предоставляемого Effect-сервиса, не произвольное значение сервиса.
- `E` — ошибки построения конкретного компонента.
- `RIn` — типизированные идентификаторы его внешних зависимостей.

Сам `DynamicLayer` — **описание**, а не мутирующий `Layer` и не живой сервис. Он не должен притворяться подтипом `Layer`. Жизнью описания управляет отдельный `DynamicRuntime`.

Функция или Effect находятся в **полях значения/конструкторах**, а не заменяют третий type parameter словом `function`.

### 5.1. Минимальная алгебра Requirement

```ts
Requirement.empty                         // Requirement<never>
Requirement.service(Database)             // Requirement<Database>
Requirement.all(
  Requirement.service(Database),
  Requirement.service(Auth)
)                                         // Requirement<Database | Auth>
```

Это небольшой неизменяемый AST известных service Tags. Он хранит доступные в runtime ключи и обеспечивает типовую связь с входами реализации. Не запускать для его вычисления произвольные пользовательские эффекты.

В 0.1 достаточно Empty / Service / All. `all` должен убирать дубли одного Tag и поддерживать вложенную композицию. Пустой `all` эквивалентен `empty`.

Зависимости в типах не превращаются в runtime-данные сами собой, поэтому передавать Tag значения необходимо. Не пытайся извлечь список зависимостей из стёртого TypeScript union или приватного AST Effect.

### 5.2. Типовая проверка описания

Конструктор должен проверять:

```text
все внешние входы переданного Layer покрыты requires
выходной Tag действительно совместим с выходами Layer
acquire в fromEffect возвращает сервис нужной формы
Scope для acquire предоставляет runtime, а не пользовательский провайдер
```

Допустимо объявить дополнительные зависимости ради жизненного цикла. Нельзя пропустить используемую внешнюю зависимость. Зависимости, уже обеспеченные внутренним `Layer.provide`, повторно объявлять не требуется.

Важный type-test: компилятор не должен «лечить» пропущенную зависимость расширением generic до `unknown`/`any`. При необходимости использовать отдельный вывод типов для requires и `NoInfer`/проверку остатка входов.

Не требовать от потребителя casts для обычного сценария. Гетерогенный реестр неизбежно стирает часть типов: такую границу локализовать в `internal/erased.ts`, документировать и подкрепить runtime-проверками ключей/наличия опубликованного Tag. Публичный API не превращать в `any`.

## 6. Желаемый API

**Все имена `DynamicLayer`, `Requirement`, `DynamicRuntime` ниже относятся к создаваемой библиотеке, а не к существующему пакету Effect.** Предпочтительно сохранить эту форму API; корректность типов важнее точного количества скобок.

### 6.1. Обычный Layer как реализация

```ts
import { Context, Effect, Layer, SubscriptionRef } from "effect"
import { DynamicLayer, DynamicRuntime, Requirement } from "dynamic-layer"

class Database extends Context.Tag("example/Database")<
  Database,
  { readonly label: string }
>() {}

class Analytics extends Context.Tag("example/Analytics")<
  Analytics,
  { readonly read: Effect.Effect<string> }
>() {}

const databaseLayer = (label: string) =>
  Layer.scoped(
    Database,
    Effect.gen(function* () {
      yield* Effect.log(`acquire database ${label}`)
      yield* Effect.addFinalizer(() => Effect.log(`release database ${label}`))
      return { label }
    })
  )

const analyticsLayer = Layer.effect(
  Analytics,
  Effect.gen(function* () {
    const db = yield* Database
    return { read: Effect.succeed(`analytics using ${db.label}`) }
  })
)

const program = Effect.scoped(
  Effect.gen(function* () {
    const enabled = yield* SubscriptionRef.make(true)
    const runtime = yield* DynamicRuntime.make()

    yield* runtime.register(
      DynamicLayer.fromLayer(Analytics)({
        id: "analytics",
        requires: Requirement.service(Database),
        when: enabled,
        layer: analyticsLayer
      })
    )

    yield* runtime.awaitState("analytics", "Pending")

    yield* runtime.register(
      DynamicLayer.fromLayer(Database)({
        id: "database",
        requires: Requirement.empty,
        layer: databaseLayer("A")
      })
    )

    yield* runtime.awaitState("analytics", "Active")
    yield* runtime.use(Analytics, (service) => service.read)

    yield* runtime.disable("database")
    yield* runtime.awaitState("database", "Disabled")
    yield* runtime.awaitState("analytics", "Pending")

    yield* runtime.enable("database")
    yield* runtime.awaitState("analytics", "Active")

    yield* runtime.replace(
      "database",
      DynamicLayer.fromLayer(Database)({
        id: "database",
        requires: Requirement.empty,
        layer: databaseLayer("B")
      })
    )

    yield* runtime.awaitState("analytics", "Active")
    yield* runtime.use(Analytics, (service) => service.read)

    yield* SubscriptionRef.set(enabled, false)
    yield* runtime.awaitState("analytics", "Pending")

    yield* SubscriptionRef.set(enabled, true)
    yield* runtime.awaitState("analytics", "Active")
  })
)

// В исполняемом example обработать Exit/ошибки и выполнить program.
// Закрытие внешнего Scope должно закрыть runtime в правильном порядке.
```

Это форма acceptance example. Агент обязан включить реальный `examples/basic.ts` в typecheck и запустить его. Строки логов — только иллюстрация; счётчики и инварианты проверяются отдельными тестами.

### 6.2. Effect вместо вручную созданного Layer

Второй конструктор — тонкая оболочка над scoped acquisition:

```ts
const analytics = DynamicLayer.fromEffect(Analytics)({
  id: "analytics",
  requires: Requirement.service(Database),
  acquire: Effect.gen(function* () {
    const db = yield* Database
    return { read: Effect.succeed(`analytics using ${db.label}`) }
  })
})
```

Он должен сводиться к тому же исполнительному механизму, что и `fromLayer`, концептуально через `Layer.scoped`. Не создавать отдельный lifecycle для Effect-реализации.

### 6.3. Effect, вычисляющий рецепт слоя

Не вводить третий несовместимый механизм. В Effect v3 это уже выражается через `Layer.unwrapEffect` или `Layer.unwrapScoped`: [S1]

```ts
const selectedLayer = Layer.unwrapEffect(
  Effect.gen(function* () {
    const config = yield* BackendConfig
    return config.mode === "remote" ? RemoteAnalyticsLive : LocalAnalyticsLive
  })
)
```

Такой рецепт передаётся в `DynamicLayer.fromLayer`. `requires` покрывает оставшиеся внешние входы **всего** рецепта. При статическом union входов обеих ветвей 0.1 консервативно требует этот union. Ветвление Layer не означает автоматического отслеживания только выбранной runtime-ветви.

Выбирающий Effect выполняется при новой сборке поколения. Он не выполняется постоянно, и обычное изменение скрытой переменной не запускает rebuild. Для такого изменения нужна замена config-провайдера, explicit replace или observable gate.

## 7. Контракт DynamicRuntime

`DynamicRuntime.make()` возвращает scoped Effect. Живой runtime не создаётся при импорте модуля. Два runtime в одном процессе полностью независимы.

Минимальный публичный набор:

| Операция | Смысл |
|---|---|
| `register(description)` | Проверить описание и атомарно добавить его в desired graph. По умолчанию enabled. |
| `enable(id)` / `disable(id)` | Изменить desired enablement. Повтор одинаковой команды — no-op. |
| `replace(id, description)` | Атомарно сменить рецепт, сохранив node id и предоставляемый service key. |
| `unregister(id)` | Отозвать компонент, дождаться корректной внутренней очистки перед окончательным удалением его runtime-записи. |
| `retry(id)` | Разрешить новую попытку после failed acquisition для того же набора входов. |
| `snapshot` | Получить immutable диагностический snapshot, без объектов сервисов. |
| `changes` | Поток актуальных snapshots; начальное состояние и дальнейшие версии. |
| `awaitState(id, state)` | Дождаться состояния, с корректной отменой ожидания и ошибкой при удалении/закрытии runtime. |
| `awaitIdle()` | Барьер: на наблюдаемом шаге нет незавершённых lifecycle-операций или уже принятых необработанных изменений. |
| `use(tag, callback)` | Выполнить Effect с закреплённым текущим поколением сервиса и управляемой отменой. |
| `shutdown` | Idempotent ordered shutdown; также вызывается при закрытии owning Scope. |

### 7.1. Подтверждение команды не равно завершению I/O

`register`, `enable`, `disable`, `replace`, `unregister`, `retry` подтверждают **приём и применение desired-state изменения контроллером**, а не завершение всех acquisition/finalizers.

Однако отозвание старых публикаций при invalidating-команде входит в тот же атомарный шаг. После успешного возврата `disable` новый `use` не должен получить старое поколение затронутой ветки.

`awaitState` и `awaitIdle` используются отдельно. Не оставляй этот контракт неявным.

`awaitIdle` не означает «все узлы Active»: допустимы Pending/Disabled/Failed. Он не ждёт завершения долгоживущих рабочих fibers или control-подписок. Будущие внешние изменения могут сразу нарушить idle; это не блокировка мира.

Изменение `SubscriptionRef` подтверждается самим ref, а не контроллером runtime. Поэтому после `SubscriptionRef.set` нужно дождаться соответствующего состояния, а не предполагать синхронную обработку gate.

`awaitState` должен сначала проверить искомое состояние. Если вместо ожидаемого состояния узел переходит в Failed, ожидание должно завершаться диагностируемой ошибкой, а не висеть бесконечно. Ожидание самого Failed допустимо. Предоставь возможность обернуть ожидание обычным Effect timeout.

После перехода runtime в Closing новые управляющие команды, новые use и ожидания невозможных состояний завершаются `RuntimeClosing`/`RuntimeClosed`, а не теряются в очереди. Неизвестный id — явная ошибка.

## 8. Состояния узла

Используй discriminated union, не набор независимых boolean-полей:

```text
Disabled — desiredEnabled=false, живого поколения уже нет.
Pending  — enabled, но отсутствуют dependencies/gate ещё не разрешает запуск.
Starting — идёт acquisition конкретного поколения.
Active   — поколение полностью построено и опубликовано.
Stopping — публикация уже отозвана; ещё идут interruption/join/release.
Failed   — диагностируемая ошибка с фазой и Cause.
```

Для Failed как минимум различать `acquire`, `gate`, `release`. `Pending` содержит причины, например `MissingService`, `DependencyNotActive`, `GateInitializing`, `GateClosed`. Состояние ссылки на зависимость с ошибкой отображать в диагностике, а не скрывать за бесконечным «loading».

Начальная enabled-регистрация — Pending до проверки условий, затем Starting при удовлетворённых входах. Failed acquisition не публикует частичный сервис.

Временный отсутствующий required service — нормальное Pending, **не исключение**.

`Disabled` выставляется только после окончания остановки. Пока выполняются finalizers, состояние Stopping, даже если desiredEnabled уже false.

Удалённый узел не остаётся навсегда в snapshot. Сохраняй внутреннюю retiring-запись, пока завершение старого поколения нужно для безопасности, затем удаляй её. Поздние сообщения идентифицируются поколением, а не совпавшим строковым id новой регистрации.

На время retiring node id и export key остаются зарезервированы. Новая регистрация с ними до окончания cleanup получает `NodeRetiring`, а не запускает параллельный экземпляр. После завершения cleanup (`awaitIdle`) их можно использовать снова. Это ограничение не отменяет проверку registration/generation identity у поздних сообщений.

## 9. Граф, поколения и идентичность

Раздели минимум три сущности:

**Описание узла:** node id, export Tag, requires, gate, рецепт, revision описания.

**Попытка/поколение:** уникальный generation id, lifecycle Scope, build fiber, выбранные входные поколения, статус, cancellation token/epoch.

**Публикация:** service key → опубликованное Active-поколение и значение сервиса.

Уникальные generation id должны отличать старую и новую регистрацию одного node id. Монотонного счётчика runtime достаточно; счётчик не сбрасывается при unregister/register.

Fingerprint сборки включает как минимум:

```text
node registration identity
recipe revision / activation epoch
required service key → выбранный provider generation id
gate revision, влияющую на валидность этой попытки
```

Не использовать только object identity, количество узлов, глобальную версию реестра или boolean «dependency exists».

### Валидация графа

На `register`/`replace` построить candidate graph и до изменения действующего состояния проверить:

- уникальность node id;
- не более одного зарегистрированного провайдера каждого service key, включая disabled-провайдеров;
- отсутствие self-dependency;
- отсутствие циклов среди разрешённых ребёр зарегистрированных узлов;
- соответствие id и export key при replace.

Отсутствующие провайдеры разрешены. Если последующая регистрация такого провайдера замыкает цикл, **отклонить именно новую команду**, не ломая старое состояние.

Tag key является runtime-ключом Context; одинаковые строки могут скрывать разные TS-типы. Не молча принимать коллизии экспорта. Использовать стабильные namespaced keys и тестировать коллизии. TypeScript не доказывает безопасность произвольно загруженного JS.

## 10. Контроллер и исполнительный слой

Рекомендуемая архитектура:

```text
commands + gate updates + lifecycle completions
                        ↓
             сериализованный controller
             authoritative state + planner
                        ↓
                  start / revoke / stop
                        ↓
            управляемые Effect-исполнители
                        ↓
               completion в controller
```

Контроллер — единственный владелец изменения authoritative state и публикаций. Допустима очередь + одна controller fiber. Не запускай несколько параллельных reconcile над одной Map.

**Контроллер не ждёт долгий пользовательский I/O.** Acquisition и stop/finalizers выполняются в управляемых исполнителях и присылают completion. Иначе невозможно обработать `disable` во время зависшего `Starting`.

Не удерживай глобальный semaphore/lock во время пользовательских acquire/release/callback. Сериализация решений не должна блокировать приём отмены.

Lifecycle-команды и completion нельзя молча терять в dropping/sliding очереди. Для 0.1 допустим простой mailbox без сложного backpressure, но это ограничение нужно документировать. Диагностические snapshots — другая категория, они могут коалесцироваться при явно описанной семантике.

Функцию вычисления графа/affected closure желательно сделать чистой и тестировать отдельно от исполнения.

## 11. Алгоритм запуска и атомарной публикации

Для запуска поколения:

1. На одном шаге контроллера проверить enablement, gate и Active-публикации всех required dependencies.
2. Зафиксировать **конкретные** входные поколения и зарегистрировать Starting-поколение как их потребителя ещё до начала I/O.
3. Создать принадлежащий этой попытке Scope и новый MemoMap; учёт владения должен быть защищён от отмены между allocate и tracking.
4. Построить immutable входной Context из выбранных сервисов. Это borrowed ссылки: consumer не приобретает provider-ресурсы заново.
5. В управляемой fiber построить Layer с этим Context и Scope.
6. Перед публикацией controller повторно проверяет token, рецепт, gate и идентичность всех выбранных поколений.
7. Если всё актуально, атомарно опубликовать единственный заявленный export и выставить Active.
8. Если сборка устарела, её результат **никогда** не публиковать; закрыть принадлежащие ей ресурсы через обычный stop-путь.

Полный успех acquisition ещё не означает право публикации.

Если Layer построился, но заявленный export отсутствует в выходном Context, это `InvalidExport`/failed acquisition. Ошибку диагностировать, Scope закрыть. Не выводить доступность из одного только generic-параметра.

Зависимости остаются живы на время acquisition и rollback consumer. Нельзя закрыть provider, пока устаревший consumer всё ещё завершает собственное построение/очистку.

## 12. Инвалидация, остановка и replacement

### 12.1. Логическое отозвание раньше физического release

При потере зависимости, disable, replace или закрытии gate:

1. Найти затронутое транзитивное множество потребителей, включая Starting-поколения и управляемые пользовательские calls.
2. На атомарном шаге убрать публикации всей затронутой ветки и пометить attempts устаревшими.
3. Не допускать новые построения/вызовы на этих поколениях.
4. Остановить потребителей в обратном топологическом порядке.
5. Только после завершения потребителей закрывать providers.

Нельзя сначала закрыть DB, а затем уведомить использующий её Analytics.

### 12.2. Что значит «остановить поколение»

Нужно отменить незавершённый acquisition, дождаться его выхода/rollback, прервать и дождаться принадлежащих поколению управляемых задач, затем завершить его Scope/finalizers. Реальный механизм может использовать связанные scopes и fibers, но эти наблюдаемые гарантии обязательны.

Finalizer потребителя может использовать старый provider для завершающей операции. Provider должен оставаться живым до окончания этого finalizer.

В diamond-графе общий provider закрывается один раз и только после обоих потребителей. Остановленные соседние ветви могут очищаться параллельно, но 0.1 вправе делать это последовательно.

### 12.3. Replacement policy версии 0.1

**Stop-before-start**, с допустимым промежутком недоступности:

```text
revoke old affected branch
→ stop consumers
→ stop old provider
→ start new provider
→ start consumers against new generations
```

Не реализовывать одновременно blue/green и stop-before-start. Нет автоматического rollback на старый уже закрытый экземпляр. Если новое построение не удалось, provider становится Failed, потребители Pending.

Новый экземпляр не запускается, пока предыдущий экземпляр того же узла не завершил остановку. Это важно для портов, файловых блокировок и эксклюзивных устройств.

### 12.4. Root shutdown

Сначала запретить приём новых операций и отозвать все публикации. Остановить граф в правильном порядке, затем закрыть control-подписки/исполнителей/контроллер, разрешить ожидающие shutdown callbacks.

Не полагаться на случайный LIFO-порядок создания дочерних scopes: после нескольких replacements он не обязан совпадать с обратным топологическим порядком.

Controller должен оставаться работоспособным, пока нужны completion остановки. Нельзя сначала автоматически interrupt controller через root scope, а потом ждать от него освобождения остальных ресурсов. Подтвердить ownership-схему отдельным shutdown-тестом.

`shutdown` idempotent. Закрытие owning Scope и явный shutdown не должны выполнять release дважды.

## 13. Boolean gate: минимальная настоящая реактивность

В 0.1 поле:

```ts
when?: SubscriptionRef.SubscriptionRef<boolean>
```

Без `when` gate всегда открыт. С `when` компонент ждёт начального наблюдения ref и реагирует на последующие изменения.

Обязательная семантика:

- `false` запрещает запуск и инвалидирует активное/строящееся поколение.
- `true` разрешает запуск при наличии required services.
- Повторное `true` без смены состояния не перезапускает Active-сервис.
- `true → false → true` инвалидирует старую попытку, даже если её build завершился уже после последнего true.
- Gate-подписка живёт на уровне **регистрации**, а не активного поколения. Иначе после false будет некому заметить true.
- Подписка сохраняется при disable и освобождается при unregister/replace/shutdown. События подписки несут identity регистрации и revision описания; опоздавшее событие старого gate после replace игнорируется.
- Не делать раздельные `get` и «подписаться на будущие события» с окном потери изменения. Использовать `.changes`, где присутствует начальное значение. [S5]
- Не запускать I/O из callback controller при получении gate event.

Доступность — это состояние, известное контроллеру после обработки событий. Не обещать атомарность с внешним миром или немедленную реакцию на физический обрыв сети.

Если DB-клиент всё ещё зарегистрирован, но потерял соединение, библиотека не узнаёт об этом автоматически. Внешний adapter должен изменить gate или заменить/отключить provider; другой допустимый подход — стабильный сервис с reconnect внутри и типизированными ошибками операций.

Не добавлять polling loop для проверки gate.

## 14. Безопасное использование сервиса снаружи графа

Замена ссылки в Context не изменяет уже выданные JS-объекты. Поэтому не делать главным API:

```ts
const db = yield* runtime.get(Database)
// произвольное хранение db после закрытия его ресурсов
```

Публичный MVP-путь:

```ts
yield* runtime.use(Analytics, (analytics) => analytics.read)
```

Контракт use:

- Выбор Active-поколения и регистрация вызова как его потребителя — один атомарный шаг.
- При отсутствии Active-публикации — `ServiceUnavailable`, без бесконечного неявного ожидания.
- Callback запускается только после успешного admission.
- Вызов имеет собственный управляемый lifetime и очищается при успехе, ошибке и отмене caller.
- При отзыве поколения новый admission закрыт, уже допущенный callback interrupt-ится; runtime ждёт его завершения/cleanup до release провайдера.
- Отмена вследствие отзыва является interruption Effect; не маскировать её под успешный результат. Сохранять причину отзыва в диагностике.
- Callback наследует Context/FiberRefs вызывающего кода, а не случайные default-настройки controller fiber. Его дополнительные требования `R` остаются в возвращаемом типе; не стирать их.
- Scope, предоставляемый управляемой callback-операции, завершается вместе с вызовом. Scoped children вызова не должны переживать его выход.
- Не выполнять бизнес-операцию автоматически заново на новом поколении. Interruption не доказывает, что внешняя операция не произошла.

Admission и отмена caller имеют гонку: отмена между выбором поколения и стартом callback не должна оставлять вечный lease. Протокол start/admit/release должен быть подтверждён тестами, а не только happy path.

**Ограничение языка:** TypeScript не имеет линейных типов. Пользователь может сохранить service object во внешнюю переменную, вернуть его из callback или запустить неучтённый Promise. Такие escape-ы запрещены контрактом, но не могут быть полностью предотвращены типами. Не обещать память-безопасность произвольного пользовательского кода.

Рабочие fibers внутри provider должны быть scoped и учтёнными. Не использовать `forkDaemon`/`runFork` как скрытый способ обойти владение. Ошибка произвольной дочерней fiber сама по себе не равна автоматическому отзыву сервиса: универсальную health/supervision-политику в 0.1 не выдумывать. Реализация сервиса должна явно управлять своей работоспособностью.

## 15. Ресурсы, MemoMap и границы Layer interop

### 15.1. Scope на поколение

Scope принадлежит поколению, а не только строковому node id. После failed/obsolete build временный Scope не остаётся бесхозным. При `Scope.make` сразу должна существовать защищённая ответственность за последующее закрытие.

Finalizers отвечают за пользовательские ресурсы; controller отвечает за межкомпонентный порядок. Нельзя заменить одно другим.

### 15.2. MemoMap на поколение

Effect имеет публичные `Layer.makeMemoMap` и `Layer.buildWithMemoMap`. Они позволяют явно задать memoization boundary. [S1]

MVP-решение: **свежий MemoMap для каждого нового поколения компонента**. Внутри одной сборки обычное разделение одинаковых sublayers сохраняется; через поколения sharing автоматически не переносится.

Причина выбора: один и тот же Layer object может строиться с Database#1 и затем Database#2. Глобальное неосторожное memoization способно оставить старую реализацию/входы. Не считать `Layer.fresh` волшебным решением без теста.

Межкомпонентный sharing осуществляется через опубликованный provider и ссылки на его поколение. Не подставлять исходный provider Layer в каждого consumer так, чтобы DB приобреталась повторно.

### 15.3. Поддерживаемый поднабор Layer

Поддерживаются обычные service-producing Layer, scoped acquisition, обычная внутренняя Layer-композиция и effectful выбор рецепта с известными оставшимися входами.

Не обещать, что построение Layer в отдельной fiber и извлечение одного Context воспроизводят все эффекты `Layer.provide` над FiberRefs, logger/tracer/config-provider и runtime flags вызывающего кода. Их propagation — отдельная семантика.

Для 0.1:

```text
service Context dependencies — поддерживаются;
ресурсы поколения — поддерживаются;
статическая среда построения runtime — фиксируется и документируется;
произвольные FiberRef-патчи provider → downstream runtime — не обещаются.
```

Сервисы примеров захватывают свои dependencies в acquisition. Если метод сервиса сам возвращает Effect с дополнительными requirements, эти requirements не исчезают магически из `runtime.use`.

Interop-ограничения должны быть в README. Не экспортировать универсальный «живой ManagedRuntime<R>», который якобы безопасно обновляет уже захваченные зависимости.

## 16. Ошибки, повторные попытки и некооперативный код

### 16.1. Failed acquisition

Сохранить `Cause`, phase, generation, fingerprint и время/порядковый номер попытки. Очистить частично приобретённые ресурсы. Не завершать весь DynamicRuntime из-за ошибки одного компонента.

По умолчанию **нет бесконечного автоматического retry**. На одном и том же fingerprint после ошибки остаёмся Failed. Новая попытка разрешается:

```text
явным retry(id);
реальным изменением соответствующего входного поколения;
новым activation cycle gate/enablement;
replace описания.
```

Изменение независимой ветки графа не является основанием повторить failed acquisition.

`retry` для Active/Pending/Disabled — явно документированный no-op либо типизированная ошибка; выбрать один вариант и зафиксировать тестами. Предпочтение: no-op, без скрытого restart Active.

### 16.2. Defect, interruption, release error

Не терять различие между typed failure, defect и interruption. Не превращать все Cause в строку; строка — только диагностическое представление.

Interruption устаревшей попытки — нормальный stop-путь, а не новый повод бесконечно перезапускать сервис.

Ошибка finalizer должна остаться видимой как release failure. Не писать `catchAllCause(() => Effect.void)` для того, чтобы snapshot стал зелёным. Не перезапускать узел автоматически после release failure: состояние внешних ресурсов неизвестно. Для 0.1 допустимо потребовать пересоздание runtime после такой ошибки.

Остальные независимые cleanup-операции должны быть предприняты; итог shutdown с release failures не выдавать за полностью успешный. Порядок означает ожидание выхода потребителя и его cleanup-попытки, но не доказательство успешного освобождения неисправного внешнего ресурса.

### 16.3. Uninterruptible/foreign operations

Произвольный некооперативный код невозможно безопасно «убить» средствами этой библиотеки. Если build/callback/finalizer не завершается, соответствующая ветка может остаться Stopping, а shutdown — ожидать.

Timeout может ограничить ожидание пользователя или дать диагностику, но сам по себе не разрешает закрыть provider под всё ещё работающим consumer и не делает unsafe-код безопасным.

У `Effect.acquireRelease` есть особенности interruptibility acquisition/release; проверь их в установленной версии. Не пиши тест «acquireRelease(Effect.never) обязан мгновенно отмениться» без понимания API. Для детерминированного interruption-теста используй явно interruptible участок с Deferred. [S7]

Lifecycle callbacks не должны ждать собственное достижение Active/Idle или инициировать циклические управляющие операции. Reentrant graph mutation из acquire/release не поддерживается в MVP; это ограничение должно быть документировано.

## 17. Диагностика и обязательные инварианты

Для node-local ошибок гетерогенный snapshot может хранить `Cause<unknown>`: тип `E` сохраняется в описании/реализации конкретного компонента, но общий runtime не должен обещать статически известный union ошибок всех будущих регистраций. Ошибки построения не подмешиваются задним числом в тип уже завершившегося `register`; они наблюдаются через состояние и ожидания.

Snapshot как минимум содержит:

```text
runtime state: Running / Closing / Closed / CloseFailed
monotonic snapshot version
для узла: id, export key, requires, desiredEnabled, lifecycle state
generation id, recipe revision, выбранные dependency generation ids
pending reasons
последняя ошибка и phase
число живых поколений/attempts и managed calls
```

Не публиковать сами service objects, секреты конфигурации или содержимое бизнес-запросов. Ошибки могут содержать чувствительные данные: предусмотреть документированный формат безопасного summary, не сериализовать произвольные объекты бесконтрольно.

`changes` предназначен для состояния, не для аудиторского event log. Можно использовать bounded/coalescing доставку snapshots с монотонной версией; потребитель должен иметь возможность получить текущий snapshot. Критичные внутренние lifecycle-события так терять нельзя.

**Инварианты, которые должны быть сформулированы в тестах:**

| ID | Инвариант |
|---|---|
| I1 | Active-публикация принадлежит только завершившему acquisition, неотозванному поколению. |
| I2 | Опубликованный consumer ссылается на те же ещё опубликованные поколения dependencies, что были выбраны при его запуске. |
| I3 | При инвалидации публикации всей affected closure отзываются до нового admission. |
| I4 | Provider не закрывается, пока есть использующие его tracked consumers/builders/calls. |
| I5 | Старый completion не публикуется после replace/disable/gate cycle/unregister. |
| I6 | У одного узла нет двух одновременно работающих поколений; у service key не более одной публикации. |
| I7 | Каждому созданному Scope соответствует известный владелец и cleanup-путь. |
| I8 | Конкретный зарегистрированный finalizer вызывается ровно один раз в обычных тестовых сценариях. Это не обещание успеха любого внешнего release. |
| I9 | Незатронутые поколения сохраняют идентичность и не повторяют acquisition. |
| I10 | Неудачная регистрация/замена оставляет desired graph и текущие публикации неизменными. |
| I11 | При успешном shutdown нет живых tracked scopes, calls, gate watchers и lifecycle workers. |
| I12 | Ошибки и незавершённая очистка не скрываются под Active/Closed. |

Не трактовать I2 как запрет на существование retiring consumer с уже отозванным provider: старые объекты могут временно оставаться физически живы для безопасной очистки. I2 относится к **опубликованному** графу.

## 18. Acceptance tests

Все конкурентные сценарии строить на `Deferred`, управляемых fibers и проверке порядка событий. Не использовать случайные sleeps как средство синхронизации. `TestClock` — для времени, а не вместо causal barriers.

| ID | Сценарий и ожидаемый результат |
|---|---|
| T01 | Нет зависимостей: register → Active; shutdown вызывает release ровно один раз. |
| T02 | Consumer зарегистрирован раньше provider: Pending, acquisition не выполняется. |
| T03 | Provider появился: цепочка стартует в топологическом порядке. |
| T04 | Disable корня цепочки: публикации отозваны, release в порядке ViewModel → Analytics → Database. |
| T05 | Re-enable создаёт новые generation ids; используются новые ссылки. |
| T06 | Замена provider пересобирает транзитивных consumers, независимая ветка не меняется. |
| T07 | Diamond-граф: общий provider приобретается один раз и закрывается после обоих consumers. |
| T08 | Частично успешный acquisition затем fail: все зарегистрированные cleanup выполнены, публикации нет. |
| T09 | Typed failure и defect acquisition отражаются как разные Cause, runtime остаётся работоспособным. |
| T10 | Failed не уходит в retry loop от snapshot/gate duplicate/изменения независимого узла. |
| T11 | Явный retry создаёт одну новую попытку; смена нужного provider разрешает новую попытку. |
| T12 | Gate false при регистрации: Pending, build не начат. True запускает узел. |
| T13 | True → true не перезапускает; false → true после остановки создаёт новое поколение. |
| T14 | Gate-подписка переживает остановку поколения и disable, но удаляется при unregister/shutdown. |
| T15 | Lost wake-up: изменение gate во время подключения наблюдателя не теряется. |
| T16 | Build удержан Deferred; disable приходит до его окончания: старое поколение никогда не публикуется. |
| T17 | Build удержан; required provider заменён: завершение build со старым входом отклонено и очищено. |
| T18 | Gate true → false → true при удержанном build: нельзя принять старую попытку по одному последнему true. |
| T19 | Быстрые replace/disable/enable обрабатываются согласованно; публикация соответствует последнему допустимому поколению. |
| T20 | Controller обрабатывает disable/snapshot, пока другой узел находится в долгом acquisition. |
| T21 | Consumer finalizer обращается к provider: provider ещё жив до завершения finalizer. |
| T22 | Дубликат id/export key, self-cycle, обычный цикл, цикл после появления отсутствующего provider — явная ошибка без частичной mutation. |
| T23 | Во время retiring повторная регистрация id/key получает NodeRetiring; после cleanup разрешена. Поздний completion старой регистрации не касается новой. |
| T24 | Повтор enable/disable/shutdown не создаёт лишние acquisition/release. |
| T25 | Один и тот же Layer object с новым dependency Context собирается заново и не использует старый MemoMap. |
| T26 | Внутри одного Layer повторно использованный sublayer сохраняет обычное sharing. |
| T27 | use на отсутствующий/отозванный сервис завершается ServiceUnavailable и не запускает callback. |
| T28 | use, конкурентный с replace: либо отклонён, либо привязан к одному поколению; нет use-after-release. |
| T29 | Отмена caller во время admission/работы use освобождает tracking и scoped children. |
| T30 | Revocation прерывает существующий managed call, ждёт его cleanup; бизнес-callback не повторяется автоматически. |
| T31 | use сохраняет caller Context/FiberRefs; дополнительный requirement не исчезает из типа. |
| T32 | Дочерняя scoped fiber сервиса живёт после acquisition и останавливается при stop поколения. |
| T33 | Shutdown при Starting/Stopping и при нескольких заменах корректно завершает все обычные cooperative операции. |
| T34 | Release defect виден; отсутствует ложный успешный Closed/автоматический restart. |
| T35 | Контролируемая uninterruptible операция удержана Deferred: ветка остаётся Stopping; после ручного отпускания корректно завершается. Тест не зависает навсегда. |
| T36 | Два runtime с одинаковыми Tags/id не влияют друг на друга. |
| T37 | Missing external requirement, неверная форма acquire, неверный output Tag — отрицательные type-tests. |
| T38 | Layer с уже обеспеченными внутренними dependencies принимается; обычный пользовательский API не требует casts. |
| T39 | Не менее 100 циклов register/replace/disable/enable/unregister/shutdown на тестовом ресурсе: баланс acquire/release, отсутствие tracked leaks. |
| T40 | awaitState/awaitIdle корректно отменяются, не висят после unregister/shutdown и не считают Pending ошибкой сами по себе. |

Дополнительно желательно property/model-based тестирование чистого planner на небольших случайных DAG и последовательностях команд с фиксированным seed. Не подменять им детерминированные concurrency-тесты.

Type-tests должны действительно выполняться через TypeScript/подходящий test runner. `@ts-expect-error` без включения файла в typecheck не является тестом.

## 19. План реализации

### Этап 0 — проверка примитивов и API

Зафиксировать версии, выполнить compatibility spike, написать минимальные положительные и отрицательные type-tests. ADR о границе между нашей семантикой и встроенными Reloadable/LayerMap. Не исследовать бесконечно: после исполняемого подтверждения переходить к реализации.

### Этап 1 — модель и чистый planner

Requirement AST, opaque DynamicLayer descriptor, node/generation identity, candidate graph validation, топологический порядок, affected closure. На этом этапе не создавать собственную систему ресурсов.

### Этап 2 — acquisition и ordered teardown

Один controller, управляемые workers, свежие Scope/MemoMap, публикация только через controller, register/enable/disable/shutdown. Сделать основную цепочку и diamond, включая failed acquisition.

### Этап 3 — изменение графа и конкурентные случаи

Replace/unregister, generation tokens, optimistic validation перед publish, гонки Starting/Stopping, обработка ошибок release. Без этих тестов нельзя переходить к заявлению «горячая замена работает».

### Этап 4 — gate и managed use

SubscriptionRef gate правильного lifetime; callback admission/revocation/cancellation; сохранение caller context. Если API приходится уточнить, обновить examples, type-tests и ADR одновременно.

### Этап 5 — пакет, документация, полный прогон

Публичные exports, declaration files, проверка внешнего потребителя собранного пакета, examples, README, ограничения, release checklist. Версия остаётся experimental.

Для каждого этапа обновлять `docs/status.md`: выполнено, команды и результаты, ограничения. Не помечать непроверенные пункты как завершённые. Если среда блокирует установку/тестирование, оставить воспроизводимые команды и честный статус, а не фиктивный зелёный отчёт.

## 21. Definition of Done

Выпуск 0.1 завершён, когда одновременно выполнено следующее:

**Приёмка завершена:** результаты проверок и матрица T01–T40 — в [docs/status.md](docs/status.md). По явному решению владельца использованы Effect `4.0.0-rc.115` и Bun вместо исходного baseline v3/pnpm/Vitest; уточнения семантики зафиксированы в ADR.

- [x] Зафиксирована и реально проверена одна major-линейка Effect, нет смешения v3/v4 API.
- [x] Оба конструктора fromLayer/fromEffect используют одну lifecycle-реализацию.
- [x] register/enable/disable/replace/unregister/retry реализованы, не заглушены.
- [x] Boolean gate действительно реактивен и не теряет наблюдение после остановки сервиса.
- [x] Все обязательные acceptance tests проходят; нет пропущенных тестов, маскирующих недоделанные гарантии.
- [x] Есть отдельные доказательные тесты stale publication, reverse teardown и use/admission cancellation.
- [x] Обычный API не требует `any`/casts у пользователя; отрицательные type-tests исполняются.
- [x] Не пересоздаются независимые ветви и не возвращаются старые memoized сервисы.
- [x] На успешном cooperative shutdown баланс acquired/released ресурсов сходится, tracked fibers/scopes/calls отсутствуют.
- [x] Ошибки release и некооперативное завершение не скрыты и не объявлены успешными.
- [x] Работают exports, declarations и внешний consumer собранного пакета.
- [x] README объясняет гарантии, ограничения, interruption внешних операций и запрет на service escape.
- [x] Есть рабочие basic/effect-factory/failure examples без реальной инфраструктуры.
- [x] Нет HMR, сети, БД, UI, arbitrary plugin loader или других незапрошенных подсистем.

## 22. Возможное продолжение после 0.1 — не реализовывать сейчас

Следующий осмысленный шаг — более выразительная **отслеживаемая алгебра требований**, а не произвольный `when: Effect<boolean>`:

```text
service(tag)
optional(tag)
all(...)
map(requirement, pureFunction)
choose(observableSelector, declaredBranches)
```

Для optional нужно заранее определить, пересоздаётся ли consumer при появлении optional dependency. Для choose — как фиксируются прочитанные зависимости, когда меняются подписки, как предотвращаются lost wake-ups/cycles и как инвалидируются старые поколения.

`Requirement.gen` возможен только с контролируемыми yielded primitives и явным tracking. Обычный `Effect.gen` нельзя объявить автоматически реактивным, потому что внутри он может читать произвольное внешнее состояние.

Другие направления: ограниченные retry/backoff-политики, multi-export, несколько провайдеров с явной selection policy, адаптеры observable config/health, API inspection, Effect v4 port. Каждое требует своей семантики, а не новой строки в feature list.

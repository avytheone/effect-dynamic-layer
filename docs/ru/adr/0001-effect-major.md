# ADR 0001: одна версия Effect для выпуска 0.1

[English](../../adr/0001-effect-major.md) | **Русский**

- Статус: принято
- Дата: 2026-09-11

## Контекст

В исходном описании проекта предлагалось использовать Effect 3.x и не устанавливать предварительную версию без отдельного решения. Позже пользователь явно изменил это требование: первую версию библиотеки нужно разрабатывать только для опубликованного пакета `effect@4.0.0-rc.115`.

Одновременная поддержка Effect 3 и Effect 4 усложнила бы типы и помешала бы однозначно проверить совместимость. При ошибке было бы трудно понять, относится ли она к самой библиотеке или к различиям между двумя основными версиями Effect.

Установленный пакет проверен локально. Он сообщает версию `4.0.0-rc.115`, запрещает доступ к `effect/internal/*` через поле `exports` и содержит открытые исходники своих общедоступных модулей. Проверка также выявила важные отличия от исходных предположений:

- ключ сервиса создаётся через `Context.Service`;
- модуля `Reloadable` в этой версии нет;
- `ScopedRef` и `LayerMap` доступны через корневые экспорты пакета.

## Решение

1. В выпуске 0.1 поддерживать только точную версию `effect@4.0.0-rc.115`.
2. Импортировать только общедоступные модули пакета `effect`. Код библиотеки не должен обращаться к `effect/internal/*` или разбирать закрытое внутреннее представление `Layer`.
3. Точные сигнатуры сверять с общедоступными исходниками установленной версии. Поведение, важное для библиотеки, дополнительно подтверждать исполняемыми проверками совместимости в Bun.
4. Не добавлять совместимые псевдонимы для Effect 3 и не заявлять поддержку диапазона версий, который на самом деле не проверен.
5. Перед переходом на другой выпуск-кандидат или стабильную версию заново выполнить всю проверку совместимости. Только после этого отдельным решением менять диапазон зависимости и документацию.

## Последствия

Преимущества:

- реализация опирается на одну понятную систему типов и один набор средств для конкурентного выполнения и управления ресурсами;
- несовместимость обнаруживается до того, как на ошибочных предположениях будет построен механизм управления `DynamicRuntime`;
- Effect остаётся внешней зависимостью, поэтому в сборку библиотеки не попадает вторая копия его механизма выполнения.

Ограничения:

- интерфейсы выпуска-кандидата могут измениться до стабильного релиза;
- приложению, использующему библиотеку, нужна та же точная предварительная версия Effect;
- поскольку `Reloadable` отсутствует, семантику изменяемого графа приходится реализовывать самостоятельно, а не через адаптер к старому модулю.

## API, на которые опирается решение

- `Context.Service`, `Context.Reference`;
- `Layer.makeMemoMap`, `Layer.buildWithMemoMap`;
- `Scope.make`, `Scope.close`;
- `Effect.forkChild`, `Effect.forkIn`, `Effect.forkScoped`;
- `Fiber.await`, `Fiber.join`, `Fiber.interrupt`;
- `SubscriptionRef.changes`;
- `ScopedRef`, `LayerMap`.

Точные способы применения этих API и результаты исполняемых проверок приведены в `docs/compatibility.md`.
